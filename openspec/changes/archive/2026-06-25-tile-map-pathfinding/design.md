## Context

Текущая симуляция: юниты движутся по прямой к случайным целям на поле 800×600. Нет препятствий. Новая функциональность добавляет сетку тайлов 25×19 (32×32 px, поле 800×608), где ~12% ячеек непроходимы. Юниты используют A* для построения пути в обход препятствий.

Проект: Rust/WASM (crates/core) + Vite/React (src/). ECS на bevy_ecs.

## Goals / Non-Goals

**Goals:**

- TileMapResource с сеткой 25×19, генерация по seed, конвертация world↔tile координат
- A* pathfinding на сетке (Manhattan distance)
- Замена Target → Path с waypoints в мировых координатах
- Система move_along_path: движение по waypoints, при пустом пути → TargetReached
- Система find_path_action: при TargetReached → генерация случайной цели, A*, сохранение пути, ретаргет при неудаче
- WASM API: getTileMap() + seed в createGameWorld
- Canvas: рендеринг тайлов (зелёные walkable, тёмные blocked), юниты поверх

**Non-Goals:**

- Динамическое изменение карты (разрушаемые/создаваемые тайлы)
- Разные типы тайлов (только walkable/blocked)
- Многослойная карта
- Редактор карт
- Оптимизация A* сверх базовой (сетка 25×19 — 475 ячеек, A* без оптимизаций работает мгновенно)
- Диагональное движение (Manhattan + 4-связная сетка)

## Decisions

1. **4-связная сетка (вверх/вниз/влево/вправо)** вместо 8-связной
   - Почему: Manhattan distance + 4-связная даёт более естественные прямоугольные пути для тайловой карты. Упрощает A*.
   - Альтернатива: 8-связная с Euclidean distance — менее предсказуемые пути через углы.

2. **Path в мировых координатах (f32)** вместо tile-координат
   - Почему: существующая Position, системы движения и WASM API работают с f32. Центры тайлов конвертируются в мировые координаты при построении пути. Это минимизирует изменения в остальном коде.
   - Альтернатива: хранить tile-координаты в Path и конвертировать при движении — больше конверсий туда-обратно.

3. **A* — собственная реализация** без внешнего крейта
   - Почему: сетка 25×19 — 475 ячеек, A* тривиален. Внешняя зависимость неоправдана.
   - Аглоритм: `BinaryHeap` для open set, `FxHashMap` или `Vec<Option<...>>` для closed set и предков.

4. **find_path_action — отдельная система**, не встроена в move_along_path
   - Почему: разделение ответственности. move_along_path только двигает. find_path_action реагирует на TargetReached, находит путь, заполняет Path. Соответствует текущей архитектуре с MessageReader/Writer.

5. **Сдвиг поля по Y: 600 → 608**
   - Почему: 19 рядов × 32 px = 608. Существующее поле 800×600 не делится на 32 по высоте. FIELD_WIDTH остаётся 800, FIELD_HEIGHT становится 608 (19 × 32). Все позиции юнитов ограничиваются 0..800 x 0..608.
   - Риск: существующие юниты могут оказаться на blocked тайлах при перегенерации. Это приемлемо — они сразу начнут движение по A* к новой цели.

6. **Тайлы рендерятся на существующем canvas** (не отдельный слой)
   - Почему: canvas уже есть в UnitsCanvas. Тайлы рисуются фоном, юниты поверх. Это не требует изменения DOM или добавления новых элементов.
   - Альтернатива: два canvas (слой тайлов + слой юнитов) — избыточно для такой простой карты.

## Risks / Trade-offs

- **[Совместимость]** FIELD_HEIGHT меняется с 600 на 608. Все существующие проверки границ и тесты нужно обновить.
- **[Производительность]** A* на каждый TargetReached (50 юнитов × ~1 цель/сек = 50 A* запусков/сек). На 475 ячейках — это < 0.1ms на запуск. Безопасно.
- **[Детерминизм]** A* детерминирован (одинаковый граф + одинаковый start/goal = одинаковый путь). Ретаргет при недостижимой цели использует тот же StdRng, что и генерация — детерминизм сохраняется.
- **[Визуальный шум]** Юниты могут накладываться друг на друга, двигаясь по тайлам. Это уже есть в текущей симуляции.
